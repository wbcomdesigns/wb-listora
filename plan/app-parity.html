App — skipped, and why

Deliberate omissions with a stated reason. These are choices, not oversights.

Deferred to a later wave

  • Native push — needs the plugin's send-out, and can only be proven on a real build
  • Opening hours field — seven days × open/close/24h/closed is a screen of its own, and it is optional on every listing type
  • Social links field — repeater interface; optional everywhere
  • Photos on submit — the gallery is optional and listings are useful without it

Web-only by design

  • Admin and moderation — 85 capabilities that belong on a desktop
  • Buying credits — would trigger Apple's in-app purchase rules
  • Imports and competitor migration
  • Every site setting — the app configures nothing; it reflects what the site decides

Deferred fields are safe to defer. They are skipped when creating a listing and preserved when editing one — the app omits any field the form never drew, so it can never erase a value it cannot show you.

Plugin health — what is still half-cooked 38 open · 32 fixed

This is the half that a green app matrix hides. None of these block the app today; several would surface as the directory grows or as a site is audited.

Fixed today — a whole listing type could not be submitted. A type whose category allowlist is empty (business ships that way; the other nine carry 8–15) dead-ended the Add Listing wizard. The wizard cannot know the type at render time, so the Category select always printed as required and the JS was the only thing that ever filled it — for business it stayed empty and still demanded a choice, refusing to let anyone past Basic Info and saying nothing about why. The rule is now simply: required only if there is something to pick. BC 10180373117

Worth recording how this was first written up, because the first version was wrong: it was reported as “every business submission fails through the API”. It does not — the API accepts a listing with no category. That failure was a malformed test payload. Seeding categories for business would also have masked it, and left the next type an owner creates without categories to dead-end exactly the same way.

Three of these are structural, not bugs. A database table is created on every install and never read; a second one is created while the live feature stores its data somewhere else entirely; and a payment record has no screen anywhere. Each ships weight that does nothing.

Two things blocking an app release

The shared app foundation has no home

  • The shared code every Wbcom app is built on is referenced by a local folder path
  • Six apps depend on it the same way, so none of them can be built in the cloud
  • It is also marked private and unversioned, so it has never been prepared for publishing
  • Reference: LST-A-01

A revoked sign-in leaves the app stuck

  • Revoking someone's app access is the only documented way to sign them out
  • The app does not notice: the account screen still looks signed in while everything fails
  • No prompt to sign in again, and no way back except signing out by hand
  • Reference: LST-A-04

Latest. Since this page was first written: receipt links now expire, favourites and related listings return real cards, untyped searches return filter counts, listing statuses are published with an unknown value now rejected, and the map represents every listing at any zoom instead of an arbitrary hundred.
