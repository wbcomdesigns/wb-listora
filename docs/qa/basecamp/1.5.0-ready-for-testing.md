## Card 1 — Owners can now suspend an abusive member

<strong>Fixed</strong> — LST-F-10<br>
Repo: <code>wb-listora</code> · commits <code>80ef2d9</code> (feature), <code>0dda5d0</code> (bulk actions) · Pro <code>7abeb77</code> (audit log)<br><br>

<strong>Root cause</strong><br>
There was no suspend at all. Removing a member's capabilities did nothing, because the REST controllers gate on <code>is_user_logged_in()</code> and ownership rather than the <code>edit_posts</code>-family caps — so a capability-stripped member kept posting. The admin UI implied a control that did not exist.<br><br>
A second, separate bug surfaced while reproducing it: self-deactivation (shipped 1.2.3) was enforced in exactly one place — hiding the profile link. A member who deactivated their own account kept posting reviews, favourites and listings. Both are fixed by the same gate.<br><br>

<strong>How to test — plugin end</strong><br>
1. Users → hover a non-admin member → <strong>Suspend</strong>. Expect a notice saying they can still browse and that their existing content is untouched.<br>
2. The Listora column shows <em>Suspended</em>, the time, and the reason if one was given.<br>
3. Edit that member's profile → <em>Listora moderation</em> → tick/untick and add a reason. Reason appears in the Users list.<br>
4. Sign in as that member on the frontend. Try to post a review, favourite a listing, submit a listing, report a listing. <strong>Every one must refuse</strong> with "Your account has been suspended…". Browsing must still work.<br>
5. Reinstate → the member can post again.<br>
6. Select several members + yourself → bulk <strong>Suspend (Listora)</strong>. The notice must report the changed count AND that you were skipped.<br>
7. Listora → Audit Log shows <code>member_suspended</code> / <code>member_reinstated</code> with who did it and why.<br><br>

<strong>How to test — app end</strong><br>
8. Sign into the app as a member, then suspend them from wp-admin.<br>
9. In the app, try to post a review or save a favourite. Expect a clear message, not "Something went wrong". This is the important one: app sign-in uses Application Passwords, which bypass normal login gates, so the block has to hold there too.<br>
10. Browsing and search must still work in the app.<br><br>

<strong>Also check (regression)</strong> — a normal, unsuspended member must be completely unaffected: posting, editing and uploading all still work.<br><br>
Journey: <code>docs/qa/journeys/regression/member-suspension.md</code>

## Card 2 — Abbreviated prices were wrong

<strong>Fixed</strong> — LST-F-20<br>
Repo: <code>wb-listora</code> · commit <code>0b2c9a6</code><br><br>

<strong>Root cause</strong><br>
Rounding to the nearest whole K, which broke three ways: it <strong>overstated</strong> (1,500 showed "$2K", 1,999,999 showed "$2.0M"), it <strong>collapsed</strong> the whole 1,000–1,499 band to "$1K", and above 999,500 it printed <strong>"$1,000K"</strong>, which is not a price. Overstating is the damaging one — a listing reading $2K when it costs $1,500 loses the click.<br><br>

<strong>How to test — plugin end</strong><br>
Set a listing's price field to each of these and check the card and detail display:<br>
<code>1,499 → $1.4K</code> · <code>1,500 → $1.5K</code> · <code>1,999 → $1.9K</code> · <code>2,000 → $2K</code> · <code>9,500 → $9.5K</code> · <code>999,999 → $999.9K</code> · <code>1,000,000 → $1M</code> · <code>1,999,999 → $1.9M</code><br>
The rule: the figure shown must never be MORE than the real price. Anything under 1,000 is unchanged.<br><br>

<strong>How to test — app end</strong><br>
Nothing to test. The app formats from the site's own currency settings and never abbreviated, so it never carried this bug. Prices in the app should read exactly as before.

## Card 3 — Payments are visible, and gateway refunds reconcile

<strong>Fixed</strong> — LST-P-12<br>
Repo: <code>wb-listora-pro</code> · commits <code>03ba1a4</code> (screen), <code>725a532</code> (join) · Free <code>1104994</code> (index)<br>
<em>Needs monetization ON.</em><br><br>

<strong>Root cause</strong><br>
Payments were recorded but no screen ever read them, so an owner reconciling against Stripe had nothing to open. Separately, the refund dialog always sent payment id 0 — the id came from a credit-ledger row, which has no payment column — so the payment's refund fields could never be written.<br><br>

<strong>How to test — plugin end</strong><br>
1. Listora → Transactions. There are now two tabs: <strong>Credits</strong> and <strong>Payments</strong>.<br>
2. Payments lists date, buyer, amount, status, gateway, invoice. Refunded rows show the refunded amount under the amount.<br>
3. Filter by status, by gateway, by date range, and search an invoice number or billing email. The count line must match the rows shown, and the last page must show the correct range.<br>
4. Clear filters with no results → the empty state should say "No payments match these filters", which is different wording from a site that has never taken a payment.<br>
5. Credits tab must be unchanged, still with its four summary cards.<br>
6. Refund a credit purchase from Transactions → the payment row moves to <em>Refunded</em> with an amount and date. Refunding the same purchase twice must be refused.<br>
7. Check at 390px — no sideways scrolling.<br><br>

<strong>How to test — app end</strong><br>
Nothing to test. Payments and refunds are owner tools and stay on the web by design; buying credits in the app is not offered (Apple rules). Member credit balance in the app should be unchanged.

## Card 4 — Saved searches consolidated, and a data-deletion gap closed

<strong>Fixed</strong> — LST-P-11<br>
Repo: <code>wb-listora-pro</code> · commits <code>1b042e1</code> (privacy), <code>725a532</code> (migration)<br>
<em>Needs Advanced Search ON to see saved searches.</em><br><br>

<strong>Root cause</strong><br>
Two stores for one feature. The working feature always saved against the member; a separate database table was created on every activation and only ever held demo rows. The privacy eraser swept the table but not the member's real saved searches — so a member who exercised a deletion request kept them.<br><br>

<strong>How to test — plugin end</strong><br>
1. <strong>Upgrade case (most important):</strong> on a site that had saved searches before updating, confirm every one still appears after the update. None should vanish, duplicate, or change name.<br>
2. Save a new search as a member → it appears in their list.<br>
3. Tools → Erase Personal Data for that member → their saved searches are gone, and the report says how many were removed. The account itself must still exist.<br>
4. Demo data: <code>wp listora demo</code> seeded searches now show up in the member's actual saved-search list, which they did not before.<br><br>

<strong>How to test — app end</strong><br>
5. If the app surfaces saved searches, confirm a member's list matches the website exactly after the update.<br>
6. Otherwise nothing to test.

## Card 6 — Unlicensed sites now say the app stops working

<strong>Fixed</strong> — LST-P-22<br>
Repo: <code>wb-listora-pro</code> · commits <code>1b042e1</code>, <code>4933495</code><br><br>

<strong>What changed</strong><br>
No enforcement was added — every Pro feature still works without a licence key, by design. What changed is the notice: it used to say only that plugin updates were paused, which was incomplete, because an unlicensed site ALSO switches the mobile app off for every member.<br><br>

<strong>How to test — plugin end</strong><br>
1. With no licence key (or an expired one), open any Listora admin screen. The notice must mention updates paused, the app switched off, AND that website features are unaffected.<br>
2. Confirm website features genuinely still work without a key.<br><br>

<strong>How to test — app end</strong><br>
3. With no/expired licence, the app must refuse at connect with "requires Listora Pro with an active licence" and must not sign anyone in.<br>
4. Enter a valid key → the app connects. Members can sign in again.

## Card 7 — Silent truncation removed across lists and exports

<strong>Fixed</strong> — LST-P-05, P-10, P-28 + REST limits<br>
Repos: <code>wb-listora-pro</code> <code>24e16f7</code>, <code>596e9cc</code>, <code>c66caca</code> · <code>wb-listora</code> <code>def5b0a</code><br>
<em>Needs the relevant feature toggles ON (monetization, audit log, outgoing webhooks).</em><br><br>

<strong>Root cause</strong><br>
Several lists and exports stopped early and said nothing: the audit-log export returned only the newest 100 rows, the webhooks list capped at 50 with no way to reach the 51st, and the transactions export tried to load the entire ledger into memory. Separately, several API limits were declared but never enforced, so a request could ask for far more rows than the documented maximum.<br><br>

<strong>How to test — plugin end</strong><br>
1. With more than 100 audit-log entries, export CSV → the file must contain <strong>all</strong> of them.<br>
2. With more than 50 webhooks, the list must page to reach them all.<br>
3. Export transactions on a large ledger → the download must start promptly and complete.<br>
4. Report a listing → only the offered reasons are accepted.<br><br>

<strong>How to test — app end</strong><br>
5. Normal browsing, search and dashboard lists must behave exactly as before — same page sizes, same results. If any app screen now shows an error where it previously loaded, that IS a bug: report it with the screen name.
