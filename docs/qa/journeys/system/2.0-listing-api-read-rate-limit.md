# Logged-out reads of listing data stop at 120 a minute per IP; members and admins are never counted

2.0.0 bounds bulk scraping of listing fields. Only the handlers that carry listing fields count (`GET /listings`, `GET /listings/{id}`, related, bulk, and `GET /search`); typeahead, map clusters, listing types and the reviews list do not. A refused read says when to retry (`Retry-After`), and the wait counts DOWN while the client keeps trying (refused hits are not counted and do not move the window).

## Setup

- `ID` = a published listing ID. Record `$SITE_URL` REST root (`/wp-json/listora/v1`).
- Do the run from ONE client IP; wait 60 s before starting so no earlier window is open.
- A second shell with a logged-in cookie (`?autologin=qa_vendor_01`) for the member rung, and one for admin.

## Steps

### 1. Guests are counted (anonymous)
- **Action**: from a fresh IP window, send 121 sequential requests:
  ```bash
  for i in $(seq 1 121); do curl -s -o /dev/null -w "%{http_code}\n" "$SITE_URL/wp-json/listora/v1/listings/$ID"; done | sort | uniq -c
  ```
- **Expect**: `120 200` and `1 429`. (Reading from PHP with `REMOTE_ADDR` set shows the same split: 429 starts on the 121st counted read.)
- **On fail**: `Rate_Limiter::limit_public_reads` (`includes/class-rate-limiter.php` ~406) registered on `rest_request_before_callbacks` (`class-plugin.php` ~315); `DEFAULTS['public_read']` (~52).

### 2. The refusal is well-formed
- **Action**: `curl -si "$SITE_URL/wp-json/listora/v1/listings/$ID"` right after step 1.
- **Expect**: `HTTP 429`; header `Retry-After: <n>` with 1 <= n <= 60; JSON `{"code":"listora_rate_limit","message":"Too many requests from this network. Please try again later.","data":{"status":429,"action":"public_read","scope":"ip","retry_after":<n>}}`.
- **On fail**: `Rate_Limiter::error`, `retry_after_header` on `rest_post_dispatch`.

### 3. The wait counts down and does not grow
- **Action**: call it again after 3 s, again after 6 s, then 10 times in a row.
- **Expect**: `retry_after` strictly decreases (e.g. 52, 49, 46) and never resets upward while the client keeps hammering. After waiting the full `Retry-After`, the next read is 200 (a client that waits always gets through).
- **On fail**: `Rate_Limiter::hit` (a refused hit must not be counted).
- **fails_on**: 2394e3c (no `Retry-After` header and the window kept sliding while the client retried). Read-back: record `Retry-After` from the header on each retry; the third value is strictly lower than the first, and after sleeping exactly the first value the next call is 200. Not verified live.

### 4. Which routes count (positive and negative controls)
While still limited:
| Request | Expect |
|---|---|
| `GET /listora/v1/listings` (list) | 429 |
| `GET /listora/v1/search` | 429 |
| `GET /listora/v1/listing-types` | 200 (not listing data) |
| `GET /listora/v1/listings/<ID>/reviews` | 200 |
| the Directory page `/listings/` in a browser | 200 (server-rendered; not the REST route) |
- **Expect**: a refused read never blocks the human-facing pages, so the limit cannot lock a visitor out of the site.

### 5. Members and admins are exempt (role ladder)
| Rung | Action (same IP, within the 429 window) | Expect |
|---|---|---|
| anonymous | step 1 | 429 after 120 |
| member-owner (qa_vendor_01 cookie + nonce) | 150 reads of the same route with `wp.apiFetch` or `-H "X-WP-Nonce: ..."` | all 200 |
| member-other (dana_whitfield) | 150 reads | all 200 (accounts on one network do not share a budget) |
| administrator (control) | 150 reads | all 200 |
- **Positive control**: the anonymous rung is 429 in the same minute, so the 200s above are the exemption and not a disabled limiter.

### 6. Tunable, and restorable
- **Action**: mu-plugin `add_filter( 'wb_listora_rate_limit_config', function ( $c, $action ) { if ( 'public_read' === $action ) { $c['ip_max'] = 5; } return $c; }, 10, 2 );`
- **Expect**: the 6th guest read in a minute is 429. Remove the mu-plugin; the default returns.
- **Action**: `add_filter( 'wb_listora_rate_limit_bypass', '__return_true' );`
- **Expect**: no 429 at all (documented bypass for trusted contexts). Remove it.

### 7. Contact form uses its own, tighter limit (control)
- **Action**: 4 contact-form posts from one IP to one listing within an hour (see `customer/2.0-leads-guest-to-owner-inbox.md`).
- **Expect**: the 4th returns 429 `listora_rate_limit` "Too many messages from your network. Try again in an hour." with `retry_after` 3600; it is independent of the read limit.

## Pass criteria

1. A guest gets 120 reads per minute then 429 with `Retry-After` and the documented JSON.
2. The wait decreases and a patient client always passes.
3. Only listing-data routes count; browsing pages is never refused.
4. Members and admins are never counted; the config filter and bypass work.

## Fail diagnostics

| Symptom | Likely cause | File |
|---|---|---|
| 429 at 60 requests | two limiter registrations (each read counted twice) | `class-plugin.php` hook added twice |
| No `Retry-After` | `rest_post_dispatch` filter missing or code prefix mismatch | `Rate_Limiter::retry_after_header` |
| Members limited | `is_user_logged_in()` false in the REST context (cookie without nonce is treated as logged out) | send `X-WP-Nonce` |
| Window grows while hammering | refused hits are being written back | `Rate_Limiter::hit` |
