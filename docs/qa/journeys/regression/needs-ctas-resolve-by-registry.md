# Needs CTAs resolve through the page registry, not a hardcoded slug (BC 10190564412 / 10185680700)

Pro registers `compare` with Free's Page Registry but never registered its two
Needs pages, so six call sites resolved them with `get_page_by_path('post-need')`
and `get_page_by_path('browse-needs')`. Those return null on any site whose pages
are named anything else, and the CTA then fell back to the site home, to the CPT
archive, or vanished entirely.

**The reported slug is not the fix.** BC 10190564412 proposed changing the string
to `post-a-need`. The verification site's page is `needs-marketplace`, a third
name — so a string swap fixes one site and breaks the next. The registry adopts a
page by the **block it contains**, which is stable across every naming.

Measured before/after on a page deliberately named `submit-a-request`:

| Lookup | Result |
|---|---|
| `get_page_by_path('post-need')` | NOT FOUND -> member sent to site home |
| `wb_listora_get_page_url('post_need')` | `/submit-a-request/` |
| `wb_listora_get_page_url('browse_needs')` | `/needs-marketplace/` |

## Steps

### 1. CTAs resolve whatever the pages are called
- **Setup**: rename the post-need page to any slug that is NOT `post-need`.
- **Action**: open the member dashboard Needs tab.
- **Assert**:

```js
({
  postANeed: [...document.querySelectorAll('a')]
    .filter(a => /post a need/i.test(a.textContent)).map(a => a.href),
  browse: [...document.querySelectorAll('a')]
    .filter(a => /browse needs/i.test(a.textContent)).map(a => a.href),
})
```

- **Expect**: both point at the real pages. Neither is the bare site home.
- **Fails if**: a CTA equals `location.origin + '/'` — that is the old
  `get_page_by_path` fallback returning.

### 2. No wp-admin route is advertised to members
`listora_need` is `public => true`, and members hold `edit_listora_needs` because
that is the CPT's `create_posts` cap and they post needs from the frontend. That
combination makes WordPress render **"+ New -> Need"** in the admin bar for every
subscriber, pointing at `wp-admin/post-new.php?post_type=listora_need` — the
block editor, which is not the member journey.

This is why BC 10185680700 could not be found by grepping our source: the link is
generated by WordPress core, not by a Listora template. The CPT now registers
`show_in_admin_bar => false`.

- **Assert**, as a subscriber, on any frontend page:

```js
[...document.querySelectorAll('a')]
  .map(a => a.getAttribute('href') || '')
  .filter(h => h.includes('post-new.php') && h.includes('listora_need'))
```

- **Expect**: empty array.
- **Note**: admins keep the full CPT screen via `show_in_menu => 'listora'`; only
  the admin-bar shortcut is gone, for everyone.

### 3. The registry keys stay registered
```bash
wp eval 'foreach (["post_need","browse_needs","compare"] as $k) {
  printf("%s => %s\n", $k, wb_listora_get_page_url($k) ?: "(empty)");
}'
```
- **Expect**: `post_need` and `browse_needs` resolve whenever a page carrying the
  matching block exists. `(empty)` is correct only when no such page exists —
  every caller composes its own fallback explicitly, per the helper's contract.
