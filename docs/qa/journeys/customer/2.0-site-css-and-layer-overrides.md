# The site's own CSS reaches Listora blocks again, themes stay out, and styles are linked files

1.9.x isolation hid every ordinary customer rule on Listora classes. 2.0.0: the site's Additional CSS is printed a second time inside `@layer listora-overrides` (declared after Listora's own layer), child themes wrap their rules in that layer themselves, theme rules still cannot restyle Listora, and Listora stylesheets are separate `<link>` layered files instead of an inline `@import` (so cache plugins can combine/defer them). Short sentinels: `regression/site-css-and-theme-colour.md`, `regression/styles-linked-not-imported.md`.

## Steps

### 1. Stylesheets are linked layered files (anonymous, 1440)
- **Action**: `curl -s $SITE_URL/listings/ | grep -o '<link[^>]*listora[^>]*>' | grep -o 'href="[^"]*"'`.
- **Expect**: every Listora sheet is a `<link rel="stylesheet">` ending `.layer.css` (`listora-variables.layer.css`, `listora-components.layer.css`, `listora-base.layer.css`, `blocks/listing-grid/style.layer.css`, `blocks/listing-card/style.layer.css`, ...) plus the unlayered `listora-isolation.css` and the theme bridge `assets/css/themes/buddyx-pro.layer.css`. `grep -c '@import'` on the HTML = 0 and no inline `<style>` begins with `@import url(...listora`.
- **On fail**: `Theme_Defenses::layer_listora_styles` / `keep_listora_styles_linked` (`includes/core/class-theme-defenses.php`), `bin/build-layered-css.mjs`.

### 2. Additional CSS applies to Listora blocks (administrator sets it)
- **Action**: Appearance > Customize > Additional CSS (or `wp eval 'wp_update_custom_css_post(".listora-card{border-radius:0;background:#ffeecc}.listora-card__title{font-size:40px}.listora-btn--primary{background:#000}");'`), publish; open `$SITE_URL/listings/` logged out.
- **Expect** (computed style on the first `.listora-card`): `background-color: rgb(255, 238, 204)`, `border-radius: 0px`; `.listora-card__title` `font-size: 40px`; a `.listora-btn--primary` `background-color: rgb(0, 0, 0)`.
- **Expect**: the page HTML contains the CSS twice: once plain and once inside `@layer listora-overrides { ... }` (view source of the `wp-custom-css` style element).
- **Positive control**: without the Additional CSS the card is the token colour (not #ffeecc), so the change proves the rule is reaching the block.
- **Negative control (themes stay out)**: BuddyX Pro styles bare `input[type=text]` globally. The Listora search input `.listora-search__input` must keep Listora's own border (computed `border-top-width` / `border-top-color` equal to what `listora-components` declares), not the theme's. Compare with the same input on a page where the Listora CSS is absent (a plain theme page search field) to see the difference.

### 3. Child-theme rules apply when wrapped in the layer
- **Action**: mu-plugin (`wp-content/mu-plugins/j20-child.php`):
  ```php
  <?php add_action( 'wp_head', function () { echo '<style id="j20-child">@layer listora-overrides{.listora-card{outline:3px solid rgb(0,128,0)}}</style><style id="j20-plain">.listora-card{box-shadow:0 0 0 4px rgb(255,0,0)}</style>'; }, 99 );
  ```
- **Expect**: the card has the green outline (layered rule wins) and does NOT have the red 4px ring from the unwrapped rule that is not in the layer (the documented behaviour: unlayered theme rules on Listora classes are neutralised by the isolation reset). Remove the mu-plugin.
- **Edge**: Additional CSS that contains `@import` or `@charset` is NOT duplicated into the layer (the file would be invalid): record that such a site must wrap rules itself.

### 4. Opt-out
- **Action**: mu-plugin `add_filter( 'wb_listora_theme_isolation', '__return_false' );`
- **Expect**: Listora sheets are the unlayered `.css` versions again, no `@layer listora-overrides` copy of the Additional CSS, and ordinary theme/site CSS applies to Listora directly (documented as restoring 1.8 behaviour). Remove the mu-plugin.

### 5. Brand colour follows the theme, hover darkens it
- **Action**: read the computed `--listora-primary` on `.listora-block` and the `.listora-btn--primary` background; hover the button.
- **Expect**: equals the theme's accent (BuddyX Pro: its `--bx-*`/global colour through `themes/buddyx-pro.layer.css`); the hover colour is a darker shade of it (L* lower), not a fixed blue; light and dark mode (`body.buddyx-dark-theme`) both come from tokens.
- **Second theme**: on a scratch copy activate twentytwentyfour/five: `--listora-primary` = the theme.json primary/accent, never `#2271b1` (the fallback) when the theme declares one.

### 6. Cards, titles and links keep computed styles after the change (regression eye)
- **Expect**: with the Additional CSS removed again, card/title/button/chips/links computed styles on BuddyX Pro and the second theme equal those recorded before step 2 (spot-check 6 properties each); dark mode unchanged.

### 7. 390px and RTL
- **Expect**: no horizontal scroll; with `html[dir=rtl]` (switch site language or set `?` test locale) the `-rtl` layered twins load (`style-rtl.layer.css`) and the same Additional CSS still applies.

### 8. Every token a stylesheet reads is declared, per theme
- **Action**: `cd wb-listora && python3 bin/token-parity-check.py .` and `python3 bin/token-parity-check.py ../wb-listora-pro --with .` (the declared set is Free's); then on BuddyX Pro AND one unbridged theme read computed `--listora-primary`, `--listora-surface`, `--listora-border` and `--listora-text` on `.listora-block`.
- **Expect**: both parity runs print no undeclared `--listora-*` name and exit 0 (only the KNOBS listed in the script may be undeclared); each computed token is a non-empty colour on both themes, in light and dark, never an empty string or the browser default black on white.
- **POSITIVE CONTROL**: `python3 bin/token-parity-check.py --self-test` exits 0 and its fixture with an undeclared token is reported, so the gate can fail.
- **fails_on**: 06a37d67 (58 tokens read but never declared after the v1 to v2 migration). Not verified live.

### 9. Restore
`wp eval 'wp_update_custom_css_post(file_get_contents("/tmp/j20-css-backup.css"));'`; delete the mu-plugins.

## Pass criteria

1. Listora sheets are linked layered files; no `@import`.
2. Site Additional CSS and `@layer listora-overrides` rules win on Listora classes; unlayered theme rules do not.
3. The opt-out filter restores unlayered behaviour.
4. Brand colour and hover come from the theme; nothing changes with the CSS removed.

## Fail diagnostics

| Symptom | Likely cause | File |
|---|---|---|

| Inline `@import` back | linked twin missing, fallback import used | `layer_listora_styles` (twin existence check) |
| Theme border on search input | isolation reset broken | `assets/css/listora-isolation.css` |
