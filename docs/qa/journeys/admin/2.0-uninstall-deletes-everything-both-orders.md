# "Delete data on uninstall" leaves nothing of Listora behind, in either deletion order, and nothing of anyone else's removed

2.0.0 fixes three leaks: statuses outside `any` (expired, rejected, paused, awaiting payment) survived, the Credits SDK tables/options survived, and deleting Pro before Free (or Free before Pro) stranded the other's rows because the second uninstall could no longer read the first one's setting. Short sentinel: `regression/uninstall-removes-every-status.md`; this journey does both orders and checks collateral damage.

## Setup

1. **Baseline snapshot** (run once; compare after each uninstall):
   ```bash
   cat > /tmp/j20-snap.sh <<'EOF'
   wp eval '
   global $wpdb; $p=$wpdb->prefix;
   $q=function($sql) use($wpdb){ return (int)$wpdb->get_var($sql); };
   echo json_encode([
    "listings"      => $q("SELECT COUNT(*) FROM {$wpdb->posts} WHERE post_type=\"listora_listing\""),
    "pro_cpts"      => $q("SELECT COUNT(*) FROM {$wpdb->posts} WHERE post_type IN (\"listora_plan\",\"listora_need\",\"listora_coupon\",\"listora_badge\",\"listora_webhook\")"),
    "listora_meta"  => $q("SELECT COUNT(*) FROM {$wpdb->postmeta} WHERE meta_key LIKE \"\\_listora\\_%\""),
    "demo_attachments" => $q("SELECT COUNT(*) FROM {$wpdb->posts} a JOIN {$wpdb->postmeta} m ON m.post_id=a.ID AND m.meta_key=\"_listora_demo_content\" WHERE a.post_type=\"attachment\""),
    "listing_attachments" => $q("SELECT COUNT(*) FROM {$wpdb->posts} a JOIN {$wpdb->posts} p ON a.post_parent=p.ID WHERE a.post_type=\"attachment\" AND p.post_type=\"listora_listing\""),
    "termmeta"      => $q("SELECT COUNT(*) FROM {$wpdb->termmeta} WHERE meta_key LIKE \"\\_listora\\_%\""),
    "terms"         => $q("SELECT COUNT(*) FROM {$wpdb->term_taxonomy} WHERE taxonomy LIKE \"listora\\_%\""),
    "tables"        => count($wpdb->get_col("SHOW TABLES LIKE \"".$wpdb->esc_like($p."listora_")."%\"")),
    "options_free"  => $q("SELECT COUNT(*) FROM {$wpdb->options} WHERE option_name LIKE \"wb\\_listora\\_%\" AND option_name NOT LIKE \"wb\\_listora\\_pro\\_%\""),
    "options_pro"   => $q("SELECT COUNT(*) FROM {$wpdb->options} WHERE option_name LIKE \"wb\\_listora\\_pro\\_%\""),
    "options_credits_listora" => $q("SELECT COUNT(*) FROM {$wpdb->options} WHERE option_name LIKE \"wbcom\\_credits\\_%\" AND (option_name LIKE \"%\\_listora\" OR option_name LIKE \"%wb-listora%\")"),
    "usermeta"      => $q("SELECT COUNT(*) FROM {$wpdb->usermeta} WHERE meta_key LIKE \"\\_listora\\_%\" OR meta_key LIKE \"wb\\_listora\\_%\""),
    "CONTROL_options_other" => $q("SELECT COUNT(*) FROM {$wpdb->options} WHERE option_name NOT LIKE \"%listora%\" AND option_name NOT LIKE \"\\_transient%\" AND option_name NOT LIKE \"\\_site\\_transient%\""),
    "CONTROL_postmeta_other"=> $q("SELECT COUNT(*) FROM {$wpdb->postmeta} WHERE meta_key NOT LIKE \"\\_listora\\_%\" AND meta_key NOT LIKE \"\\_wb\\_listora%\""),
    "CONTROL_users" => $q("SELECT COUNT(*) FROM {$wpdb->users}"),
   ],JSON_PRETTY_PRINT);'
   EOF
   bash /tmp/j20-snap.sh > /tmp/j20-before.json
   ```
2. Settings > Advanced > Data Management: tick "Permanently delete all WB Listora data on plugin uninstall" (warning text "this removes every listing, review, favorite, claim, custom table, and setting. Cannot be undone."), Save. Confirm `wp option get wb_listora_settings --format=json | jq .delete_on_uninstall` is 1 and, with Pro active, `wp option get wb_listora_pro_delete_on_uninstall` is 1 (Pro mirrors the switch into its own option so it survives Free being deleted first).

## RUN 1: Free deleted first

### 1. Delete
- **Action**: `wp plugin deactivate wb-listora-pro wb-listora && wp plugin uninstall wb-listora`, then `wp plugin uninstall wb-listora-pro`.
- **Expect**: both commands succeed, no PHP warning/notice and no fatal in `debug.log` from either `uninstall.php`.

### 2. Verify
- **Action**: re-create the snapshot as `/tmp/j20-after.json` (the helper functions are not loaded now: the script above uses only core functions on purpose) and diff.
- **Expect**: `listings` 0 (every status, including expired/rejected/deactivated/payment), `pro_cpts` 0, `listora_meta` 0, `demo_attachments` 0 and `listing_attachments` 0 (images of deleted listings are removed from the media library and from disk; baseline on the dev site was 522 and 461), `termmeta` 0, `terms` 0 (categories, locations, tags, features, types, service categories), `tables` 0 (all `{prefix}listora_*` incl. `listora_credit_*` SDK tables), `options_free` 0, `options_pro` 0, `options_credits_listora` 0, `usermeta` 0, and `wp-content/uploads/wb-listora-import` removed.
- **Expect (collateral)**: the `CONTROL_*` rows are unchanged to the digit; the unrelated plugin's options/postmeta/users are intact; WooCommerce still loads.

## RUN 2: Pro deleted first (restore the scratch site to the same starting state, re-snapshot)

### 3. Delete
- **Action**: `wp plugin deactivate wb-listora-pro wb-listora && wp plugin uninstall wb-listora-pro` THEN `wp plugin uninstall wb-listora`.
- **Expect**: same final snapshot as step 2. In particular Pro's tables (`audit_log`, `coupon_usage`, `webhook_log`, `need_responses`, `search_terms`, `rate_limits`, `credit_log`), the `payments` table (Free's), roles/caps (`listora_moderator` removed, moderators demoted to subscriber), and Free's listings + `listora_*` options are gone even though Free was uninstalled last.
- **Positive control**: run the same sequence with "Delete data on uninstall" UNticked on a third scratch copy: all counts stay as in the baseline (nothing deleted), proving the checks above measure the switch and not a cleanup elsewhere.
- **Read-back** (card 10393531299): `SELECT COUNT(*) FROM wp_term_taxonomy WHERE taxonomy LIKE 'listora\_%'` is 0 and `SELECT COUNT(*) FROM wp_posts WHERE post_type='attachment' AND post_parent IN (<ids of the listings deleted>)` is 0, in BOTH run orders. **fails_on**: 9ac05f73 (categories, locations, types and listing images survived). Not verified live.

### 4. Reinstall sanity
- **Action**: install and activate Free again.
- **Expect**: activation recreates tables and the Credits SDK tables (no "table doesn't exist" errors), the setup wizard opens, nothing from before is shown.

### 5. Look-alike rows owned by someone else survive (positive control for LIKE wildcards)
- **Action**: before RUN 1 seed `wp option add wbxlistora_test 1`, `wp post meta add <any non-listing post> xlistora_test 1`, `wp user meta add 1 wbxlistora_test 1` (names that match `wb_listora_%` / `_listora_%` only if `_` is treated as a wildcard). Run RUN 1 and RUN 2 steps with "Delete data on uninstall" ticked.
- **Expect**: after each uninstall `wp option get wbxlistora_test`, the `xlistora_test` postmeta row and the `wbxlistora_test` usermeta row all still exist (value 1), while `options_free` stays 0. Negative control: `wb_listora_settings` is gone.
- **Read-back**: `SELECT COUNT(*) FROM wp_options WHERE option_name='wbxlistora_test'` = 1 and `SELECT COUNT(*) FROM wp_postmeta WHERE meta_key='xlistora_test'` = 1.
- **fails_on**: unknown (card 10393557222, no fix commit found). Not verified live.

### 6. Multisite: every subsite is cleaned, with its own types (bc-10393846493)
- **Action** (network super admin): on a 3-site network network-activate Free, give each subsite a different custom listing type and attachments, tick Delete data on each site, Network Admin > Plugins > Delete.
- **Expect**: on every subsite the tables `{prefix}_N_listora_*`, `wb_listora_*` options, listing posts and their attachments are gone; site 1's type list is not reused for subsite 2 or 3; a subsite that did not tick the flag keeps its data.
- **Read-back**: loop `wp site list --field=url` and run the baseline snapshot per `--url`; every counted key is 0 on opted-in sites and equals the "before" value on the opt-out site.
- fails_on: d71e6b86. Not verified live.
