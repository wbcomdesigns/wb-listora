## How to use this file

Every finding is a **QA card**: it has reproduction steps that stand alone, an expected-vs-actual
contract, and an explicit statement of which of the three entry points (frontend / admin / REST)
it touches. Cards are written so QA can reproduce without reading the code.

`Surfaces` uses the CLAUDE.md three-entry-point rule — **F** frontend, **A** admin, **R** REST/API.
`QA today` records whether a journey or runbook row already covers it; where it says NONE, that
surface has never been exercised and the card should carry a new journey in the same PR.

Severity: **P0** blocks release · **P1** real customer-visible defect · **P2** debt / polish.

**Environment for all repro steps:** `http://listora.local`, admin auto-login via `?autologin=1`.
Free 1.4.1 + Pro 1.4.1 both active. Current dataset is 115 listings — cards marked
`NEEDS SEEDED DATA` cannot be reproduced on this dataset and require a WP-CLI seed first.

## P1 — customer-visible defects

### LST-F-04 · Search is hard-capped at 5000 listings; rows past the cap are unreachable and `total` lies
**Surfaces: F, R · QA today: NONE at scale · NEEDS SEEDED DATA**

> ✅ **FIXED in 1.5.0 on the SQL path** · ⚠️ **the cap itself is still unexercised**
>
> Re-checked 2026-08-08 against the live API. The SQL path is genuinely fixed and the evidence below
> holds: `total` is 4,895, matching `wp post list --post_status=publish` exactly, and the last page
> returns a row. But `MAX_PHASE_1_CANDIDATES = 5000` still governs the **materialising** path, which
> any query with `open_now`, date/taxonomy/field filters or facets falls onto — and the seed is 4,895,
> which sits *under* the cap. So the plain-browse path is proven and the capped path is not.
>
> **To close this properly:** seed above 5,000 published, then re-run with a taxonomy or date filter
> applied (forcing the materialising path) and confirm `total` and the last page still agree.

> through `sql_paginated_candidates()`: a dedicated `COUNT(*)` plus a database-side
> `ORDER BY … LIMIT/OFFSET`. Verified on the seeded fixture — `/search` reports **4,895**, exactly
> matching `wp_posts`, across 245 pages, and the oldest listing is reachable on the last page.
> The frontend Directory reads "Showing 1-20 of 4,895 listings".
>
> All ten sorts moved to SQL, including the two that were at risk: **distance** (a new
> `Geo_Query::distance_sql()` mirroring the PHP haversine — verified identical to 9 decimal places
> on real rows) and **relevance** (FULLTEXT `relevance_score`). Every clause carries a
> `s.listing_id DESC` tiebreak, without which `LIMIT/OFFSET` repeats and skips rows on the
> low-cardinality sort columns; verified 25 pages x 20 rows across three sorts = 500 unique IDs,
> 0 duplicates.
>
> Queries that DO need the full candidate set — `open_now`, date filters, taxonomy filters,
> field filters, or facets — keep the materialising path unchanged. The two paths were compared
> head-to-head on the same query across six sorts: identical totals and identical page IDs,
> **0 mismatches**.
>
> The candidate SELECT/WHERE is now built once by `build_candidate_query()` and shared by both
> paths, so they cannot drift apart — the failure this file already documents for the two rival
> facet implementations (LST-F-12).

`Search_Engine` phase 1 pulls up to 5000 candidate rows into PHP, then sorts, counts, paginates and
facets **in memory**. Consumers are the entire browse surface: `blocks/listing-grid/render.php:130`
and `includes/rest/class-search-controller.php:320`.

**Evidence:** `includes/search/class-search-engine.php:37` (`MAX_PHASE_1_CANDIDATES = 5000`), `:504` (`LIMIT %d`), `:111` (`$total = count( $candidates['ids'] )`), `:117` (`array_slice` pagination)

**Repro** (needs ~20k listings)
1. Seed 20 000 published listings.
2. `curl -s "http://listora.local/wp-json/listora/v1/search?per_page=20" | jq '.total, .pages'`
3. Note the oldest listing ID in the DB, then try to reach it by paging the grid.

**Expected:** `total` equals the true published count, and every listing reachable by paging.
**Actual — VERIFIED 2026-08-07 on a seeded 5,515-listing fixture:**

```
DB published listings : 5515
/search total         : 5000        <- understated by 515
/search pages         : 250
candidate id range    : 1395 .. 6394
oldest listing (ID 15): NOT in the candidate set
```

Because the cap orders by `s.listing_id DESC`, the **oldest 515 listings drop out of unfiltered
browse** — at 20k listings that is the oldest 15,000.

**Correction to an earlier draft of this card:** it claimed those listings are "not reachable
through search, grid, or `/search` at all." That overstates it, and testing disproved it. A
*narrowing* query still finds them, because the candidate set falls under the cap before slicing —
`?q=Golden+Fork` returns exactly ID 15, `total: 1`. The defect is confined to **unfiltered or
weakly-filtered browse**: `total` is wrong, pagination stops early, and the oldest rows are
unreachable *by paging*. That is still a P1 — browse is the default state of the directory — but it
is not a total blackout, and the fix should be scoped to the counting/paging path rather than to
search as a whole.

The 5000 IDs are also re-passed as `IN (…)` placeholder lists into 3-4 follow-up queries
(`:1352` field facets, `:1400` taxonomy facets, plus `filter_taxonomies` / `phase_2_field_filter`).

**Note:** this directly contradicts the plugin's stated 100K-readiness posture and the
`plan/100k-readiness/` budget docs.

**Fix (design decision needed, not a patch):** move sort + count + pagination into SQL with a
dedicated `COUNT(*)`, and compute facets from a bounded aggregate query rather than an in-memory
ID list. Raising the constant only moves the ceiling.

**QA to add:** a seeded-scale journey asserting `total` equals the true `COUNT(*)` and that the
oldest listing is reachable. `audit/qa-coverage.json` shows 0% coverage on all 70 REST routes.

### LST-F-07 · Orphan purge is wired to nothing; deleted listings still inflate search counts
**Surfaces: F, R · QA today: cascade covered, orphan backfill NOT covered**


> ✅ **FIXED in 1.5.0** · re-verified in code 2026-08-08
>
> Re-read 2026-08-08: both `Listing_Data_Eraser` (`:69`) and `Search_Indexer` (`:51`) hook `wb_listora_daily_cleanup`.

The 1.4.1 delete-cascade (2026-08-04) is correct for new deletes. But `purge_orphans()` — the
backfill for everything deleted **before** that fix — is only reachable from WP-CLI. The daily
cleanup cron exists and fires, and `purge_orphans` is not attached to it.

**Evidence:** `includes/core/class-listing-data-eraser.php:120` (`purge_orphans()`); called only at `includes/class-cli-commands.php:284`; cron `wb_listora_daily_cleanup` fires at `includes/class-plugin.php:625` with only `prune_analytics` listening (`includes/workflow/class-expiration-cron.php:29`)

**Repro** (verified live on this DB)
```sql
SELECT x.listing_id, x.title, x.status
FROM wp_listora_search_index x
LEFT JOIN wp_posts p ON p.ID = x.listing_id
WHERE p.ID IS NULL;
-- returns: 929 | "Smoke Owner Journey Cafe" | publish
```
That listing was deleted 2026-07-26, before the cascade landed 2026-08-04.

**Expected:** zero orphan rows; deleted listings absent from search entirely.
**Actual:** the stale row survives with `status: publish`. `Search_Engine::phase_1_candidates()`
selects from `search_index` with **no join to `wp_posts`** (`class-search-engine.php:508`) and

pagination. Downstream hydration drops the missing post, so the user sees "12 results" and 11 cards.

**Customer impact:** every site that deleted listings before 1.4.1 carries these permanently,
unless an admin runs a WP-CLI command they have no reason to know exists.

**Fix:** attach `purge_orphans()` to `wb_listora_daily_cleanup` (one line), and/or join
`wp_posts` in phase 1 so orphans can never be counted.

**QA to add:** regression journey — delete a listing via SQL (simulating a pre-1.4.1 delete), run
the daily cleanup, assert 0 orphans and that `/search` `total` is correct.

- `.wbcom-i18n.json` is excluded only in `bin/build-release.sh`'s rsync, **not** in `.distignore` — any packaging path that reads `.distignore` (e.g. `wp dist-archive`) still ships the i18n-AI config.

**Not a gap (checked):** Pro added `<exclude-pattern>languages/*</exclude-pattern>` to `phpcs.xml`
and Free did not — correct asymmetry, since Free's `phpcs.xml:6-9` scans only specific paths while
Pro's scans `<file>.</file>`.

**Repro**
```bash
git show origin/1.4.2:.distignore | grep -iE 'languages|i18n'        # -> no match: nothing excludes translation sources
git ls-tree --name-only origin/1.4.2 languages/ | grep -c '\.po$'    # -> 10
git show origin/1.4.2:languages/wb-listora-tr_TR.po | wc -l          # -> 12416
git show origin/1.4.2:bin/build-release.sh | grep -n 'wbcom-i18n'    # -> :66, an rsync --exclude and the only exclusion anywhere
```

**Expected:** `.distignore` is the single source of packaging exclusions, so every packaging path
produces the same zip.
**Actual:** `.distignore` names neither `languages/*.po` / `*.pot` nor `.wbcom-i18n.json`. The `.po`
sources (10 files, 12 416 lines in tr_TR alone) ship on **both** paths, and `.wbcom-i18n.json` ships
on any path that reads `.distignore` — `bin/build-release.sh:66` is the only thing stripping it.

**Fix:** add `languages/*.po`, `languages/*.pot` and `.wbcom-i18n.json` to `.distignore`, then drop
the now-redundant `--exclude='.wbcom-i18n.json'` at `bin/build-release.sh:66` so the two packaging
paths cannot diverge again.
