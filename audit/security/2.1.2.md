# Security review: WB Listora 2.1.2

Baseline: v2.1.1. Reviewed on the 2.1.2 branch.

## G1 mechanical sweep
`security-sweep.sh --baseline v2.1.1`: no CRITICAL patterns. No count rose: sql-direct-interpolated 48, readfile-serve 1, nonce-only-auth 6, extract-call 2, no-abspath-guard 20, routes 76 / callbacks 89 (identical to v2.1.1).

## G3 diff review (v2.1.1..2.1.2)
- No register_rest_route, permission_callback, methods list or current_user_can check was added, removed or loosened in Free.
- New request input: the optional claim rejection reason (`claim_reason`) is read after the row-action nonce and the capability check, run through `sanitize_textarea_field()`, and used only as the text of the rejection email.
- `Reviews_Model` reads the report option rows with a prepared `IN (...)` list and `maybe_unserialize()` on values the plugin wrote itself (never request data).
- `Charge::announce_submitted()` and `wb_listora_announce_submitted()` only fire an action; they take a post id from server code and change no data.
- Email verification now sets the post status before the charge, so a held listing stays held; it moves no data a member did not already own.
- The credit helpers wrap reads of the member's own ledger and balance; no new route exposes another member's ledger.

## Scanner-visible but safe
- readfile-serve (1), nonce-only-auth (6), extract-call (2): unchanged from 2.1.1, each reviewed in earlier releases.

## G2 authorisation matrix
No route or capability changed, so no manifest entry changed. Live spot-check on a Free + Pro site, dispatched with `rest_do_request()`: settings, settings/billing, audit-log answer 401 to a visitor and 403 to a member; `/credits` returns only the caller's own data; need responses answer 401, 403 and 200 for a visitor, another member and the author.
