# Security review - WB Listora 1.9.0 (Free), 2026-09-30

Scope: `git diff v1.8.0..HEAD` (HEAD 3fb5bf9c, branch 1.9.0), own code only (vendor/, libs/, build/, node_modules/, tests/, languages/ excluded). 200 files, +17.9k/-6.1k. Combo install (Pro active), listora.local.

Gate E tooling (gen-openapi, rest-reachability) and the G2 enforced RouteAuthorityTest are not adopted in this repo yet; the matrix is manual, per the 1.8.0 precedent.

## Verdict

**Clear after fix.** One HIGH reachable by a subscriber (F1) was found and fixed before tagging (see F1): the new submission charge trusts a client-supplied `plan_id`, so on a site without Pro's Pricing Plans a member with 0 credits submits a saved draft and it goes to review (or live, on auto-approve) with nothing held or charged. No CRITICAL, no unauthorised read or write of another member's objects. One LOW (F2) and one INFO (F3) do not block.

## Findings

| # | Sev | Where | Story | Status |
|---|---|---|---|---|
| F1 | HIGH | `includes/rest/class-submission-controller.php:1194` (also `:771`) | Submitting a saved draft skips `charge_submission()` whenever the request carries `plan_id > 0`, and the value is never checked. A member with 0 credits saves a draft, then sends `PUT /submit/{id}` with `plan_id=999999`. Free alone has no plan handler, so the listing goes to `pending` (or `publish` on auto-approve) with nothing held, and approving it deducts nothing. Verified with cost 5 and balance 0 and Pro's Pricing_Plans callbacks removed: manual moderation gave pending, then publish after admin approval, balance 0; auto-approve gave publish, balance 0. With Pro Pricing Plans active, `require_plan_on_save` keeps it a draft, so the exposure is Free-only sites and Pro sites with Pricing Plans off. On create (`:771`) the same shortcut is harmless, because the post-insert `charge_submission()` at `:938` still runs (verified 402). This re-opens card 10336800031 ("members without credits used to list for free") on the draft path. | **Fixed before tagging.** `update_listing()` keeps the request `plan_id` only for the fail-fast balance pre-check; the real `charge_submission()` now runs after `wb_listora_listing_submitted` (Pro's plan handler), exactly like create, and a failed charge reverts the listing to draft with a 402. Mutation-proven: unfixed 200 pending/publish at balance 0, fixed 402 draft in both moderation modes; a paying member is charged exactly once (10 -> 5 auto-approve, 5 -> 0 manual, no charge on approval). Regression: `submission-cost-charged.md` step 4b + runbook `D.draft-forged-plan-id`. Original recommendation: do not skip on the request value. Drop the `plan_id` condition and rely on `wb_listora_listing_submission_cost()`, which is already 0 when a plan is really attached. Or skip only when the id is a published `listora_plan` that Pro accepted (for example, a filter Pro answers). Add a regression journey: draft + bogus plan_id + 0 balance returns 402 and stays draft. |
| F2 | LOW | `includes/rest/class-submission-controller.php:618`, `:1167`; rendered at `templates/blocks/listing-detail/tabs.php:130` | `wp_kses_post` keeps HTML comments, so a subscriber can now store block delimiters in a description. The detail tab runs `the_content`, so those blocks render server-side. Verified: `<!-- wp:rss {"feedURL":...} /-->` fetched and rendered the feed; `wp:loginout` and `wp:search` also rendered. The effect is author-level block use by a subscriber: an outbound feed/oEmbed fetch to a URL they choose (through `wp_safe_remote_*`, so private/loopback addresses are refused), plus layout injection. The final `wp_kses_post` still strips script. Shortcodes in descriptions were already honoured in 1.8.0 (`sanitize_textarea_field` keeps `[...]`). | Not blocking. Recommend limiting the blocks rendered in member-authored descriptions to an allowlist (paragraph, heading, list, image, gallery, video, embed from trusted providers), or stripping block delimiters for users without `unfiltered_html`. |
| F3 | INFO | `blocks/listing-submission/render.php:96` vs `PUT /submit/{id}` permission callback | The wizard now opens edit mode for `edit_others_posts` users, but the save route is author-only, so an admin or editor who edits another member's listing from the frontend gets a 403. This fails closed. It is a functional gap, not a security one. | Functional follow-up. |

## Scanner-visible but safe

- `Claims_Controller::change_status()`: reached only from `PUT /claims/{id}` (`manage_listora_claims`) and the admin claim actions (page guard + capability + `check_admin_referer`). Queries are prepared by id. Reversal only moves ownership back while the claimant still owns the listing.
- `wb_listora_member_review_statuses_sql()` interpolation in the dashboard controller: fixed literals, no request data.
- Term merge / type reassign SQL (`Term_Helper`, `Listing_Type_Registry::reassign_listings`): `$wpdb->prepare` with term_taxonomy_id and slugs, behind `manage_listora_types`.
- `Email_Log` counts / distinct / TRUNCATE: table name only. Its admin viewer renders bodies in `<iframe sandbox="" srcdoc="esc_attr(...)">`.
- `Credit_Lock` `GET_LOCK` / `RELEASE_LOCK`: prepared, and the name is derived from the user id.
- `Reviews_Model` / admin hub counts: table names from `$wpdb->prefix` and `%d`/`%s` placeholders.
- `Listing_Columns::any_reported()`: prepared `LIKE` with `esc_like`.
- `Migrator` credit-ledger cleanup: `%i` + literals, no request data.
- `wb_listora_listing_is_interactable()` now gates favorites, reviews (list and create) and claims on unpublished listings. Verified 404 for non-owners above.
- Review edits by a non-moderator send an approved review back to pending. An author cannot set `status` (403).
- `POST /submit` carrying another member's `listing_id` falls through to create; it never edits the target (verified).
- Settings tab reset (`DELETE /settings` `keys` / `options`): `manage_settings_permissions`. Standalone options are intersected with the filtered reset list, so a caller cannot delete an arbitrary option.

| S1 | HIGH (money) | `wb-listora.php` consumer config; SDK `Consumer::settle_holds()` | Free's `listing_submission` consumer settled every open hold on a listing, so on a paid-plan listing it consumed Pro's plan hold at publish. Pro's settle failed, the listing was parked in `listora_payment`, and the next top-up charged the plan again. Reproduced: 25 -> 15, parked; fixed: 25 -> 15, published, one "Plan: Standard" deduction. | The consumer settles/releases on its own hooks, fired only when no plan pays (`wb_listora_listing_plan_pays()`). Known ceiling: a listing given a plan after a submission hold was placed keeps that hold open. |
| S2 | MEDIUM (integrity) | `class-submission-controller.php` `submit_listing()` | A deadlock inside the submission transaction rolled the new listing back while the request carried on and answered with its id. | Post-COMMIT existence check; 503 `listora_submission_retry`.
